网络波动导致 SSE 断开，如何实现“断点续传”？

# 1. 断点续传是什么？

一句话解释：断点续传 = 传到一半断了，下次从断的地方继续，而不是从头开始。

流式聊天时：模型在“一个字一个字”往外吐。比如：

```
今
天天
天气
不错
……
```

如果网络断在“天气”这里。

断点续传的意思是：

> 恢复后从“不错”开始继续发。

而不是：

> 再把“今天天气”发一遍。

# 2. 大模型流式聊天链路

在做类豆包的流式聊天时，完整链路通常是

```
浏览器  ←(SSE)→  你的 Chat 服务  ←(SSE)→  AI 平台
```

断点续传，只发生在【浏览器  ←→  你的chat服务】,生成了一部分内容，突然网断了，点击【继续生成按钮】

# 3. 断点续传场景

## 3.1 场景一：模型没断（真正的断点续传）

浏览器断了（比如用户网断了），但模型还在生成。

### 1. 核心原理

对大模型流式输出的分片落库、记录断点位置、断点后增量推送

### 2. 实现步骤

1. chat服务里，接收大模型的流式请求时，把所有的响应delta都落库，保存消息和event的同时，再生成一个有序的sequence No

```java
message_id
sequence_no
content_chunk
created_at
```

例如：

| sequence_no | content |
| ----------- | ------- |
| 1           | 今      |
| 2           | 天天    |
| 3           | 天气    |
| 4           | 不错    |

2.  前端保存每个message记录最后一个sequence No为lastSeq

```js
{
  messageId: "xxx",
  lastSeq: 12
}
```

3. 断开后，点击【继续生成按钮】，带上 lastSeq请求接口

```js
GET /chat/recover?messageId=xxx&lastSeq=12
```

4. 后端接收请求后，从数据库查询seq > 12 的内容， 继续推送给前端

- 如果模型已经推理完成 → 直接补全
- 如果模型还在推理 → 重新订阅你自己的流

## 3.2 场景二：调用上游 AI模型断了（假的断点续传）

无法真正续传，因为：

- 大模型推理是一次性计算
- 没有“从第 234 token 继续”的能力

### 1. 核心思路

重新发一次模型请求，并且把已有内容带上。

### 2. 实现步骤

基于对话历史恢复，构建message, 

- 第一条消息，`role`为 `'user'`，`content`是用户的**原始问题**
- 第二条消息，`role`变为 `'assistant'`，`content`是 AI 助手的**中断前回复**
- 第三条消息，`role`再次变为 `'user'`，`content`是用户的**追问**——‘请继续’

```
[
  {"role":"user","content":"原始问题"},
  {"role":"assistant","content":"今天天气不错，适合"},
  {"role":"user","content":"请继续"}
]
```
